<Expandable title="The problem" label="the constraints">

A clinician finishes an appointment and has to write it up - presenting
complaint, history, exam, treatment, plan. Ninety percent of the words are
identical to the last patient's; the ten percent that differ are what
actually matters clinically, and they're the part that gets rushed, because
the other ninety still has to be typed by hand while the next patient is
already in the waiting room. A real template runs to hundreds of these
fields, all of it boilerplate a clinician re-types or re-clicks through
every single visit. Get it wrong and it isn't a typo - it's a chart error,
because a clinical note is a legal record.

<NinetyTenSplit />

<ExpandableDetail>

The constraints that shaped everything after this:

- **The output is plain text, not our format.** It has to survive being
  pasted into a twenty-year-old Windows EHR with no stray characters.
- **No install.** It runs in the browser next to 200+ healthcare
  systems, because practices can't add software to clinical machines.
- **Documents get big.** A real template is hundreds - sometimes
  thousands - of custom elements, and it has to stay responsive.
- **The users aren't software people.** Dentists use this between
  patients, often gloved, always in a hurry.
- **Nothing may be silently mangled.** A note is a legal record; a
  formatting bug is a chart error.

</ExpandableDetail>

</Expandable>

<Expandable title="The approach" label="the alternatives I ruled out">

The editor has to be a form *and* a document at the same time. You interact
with it like an app - clicking options, toggling lines on and off - and
what comes out the other end is clean prose you can paste into a
twenty-year-old Windows EHR without a single stray character. So every
template is a single document that renders two ways at once: the
interactive note a clinician clicks through, and the plain-text note the
patient record actually keeps.

<DocumentFlowDiagram />

<ExpandableDetail>

Two obvious alternatives both fail. A **plain rich text editor** means
retyping the skeleton every time - it solves nothing. A **form** stops
being a note: the output has to leave the app as plain text, because it
gets pasted into whichever of two hundred-plus patient management systems
the practice runs, and a form doesn't serialise into prose. The Slate.js
document in the middle is what's left once both of those are ruled out -
an editor that behaves like a form while it's being edited and reads like
prose on the way out.

</ExpandableDetail>

### The element set

Ten-plus custom Slate element types, all domain-specific, all of them
things a clinician actually needed rather than things a text editor
usually has:

- **Buttons** - inline option groups. Click to select, Ctrl-click for
  multi-select, right-click to *negate* an option (which is how you say
  "no caries" in one gesture instead of a sentence).
- **Clickable lines and clickable text** - content that sits in the
  template greyed out and only enters the note when it's relevant.
- **Blank inputs, single-select dropdowns, multi-select dropdowns,
  grids, toggle blocks, annotations** - the rest of the form vocabulary.
- **A speech-to-text pointer** - an element that marks where dictated
  text is going to land.

### Authoring affordances, and a context menu of our own

Authoring that by hand would be miserable, so the editor grew the
affordances of a real writing tool: a `/` command menu, keyboard
shortcuts for everything, and **Convert** - select any run of text and
turn the elements in it into buttons, or the text in it into buttons,
in one move.

The **logic panel** above is an if/else system over the custom elements:

### Dictation that lands in the right place

Transcription is the part everyone asks about, and the interesting
problem isn't the model - it's where the words go. Speech comes back
seconds later, into a document the clinician has carried on clicking
through in the meantime, so the insertion point has to be something the
document holds on purpose rather than a guess about where the cursor
used to be. That's what the pointer element is for.

The control itself is push-to-talk: hold to speak, drag it anywhere on
screen, slide to lock it open, auto-stop on silence - designed for
someone holding a mirror in their other hand.

### The AI layer, and the rule it has to obey

Three model-backed features sit on top of the note.

- **Summarisation** collapses a long, dictated, circling account of an
  appointment into the tight clinical summary that actually belongs in
  the record.
- **Cleanup** removes the debris dictation leaves behind - false starts,
  duplicated phrases, stray punctuation, sentences that trail off -
  without touching clinical meaning. This is the one where being
  helpful is dangerous. A model that tidies the phrasing of a drug dose
  is a model that has to be fenced in.
- **Auto-format** is Prettier for clinical notes: consistent spacing and
  blank lines between sections, consistent capitalisation of headings
  and abbreviations, and none of the double spaces and orphaned
  punctuation that a half-clicked option leaves behind. Deterministic
  wherever it can be, so the same note always comes out the same shape.

<Callout label="The rule">
  A model returns text. The document is a tree. Dropping a rewritten
  block straight into the selection would flatten every button, dropdown
  and clickable line inside it into dead prose - the template would come
  back looking fine and be permanently broken. So each of these runs
  over a resolved range and writes back as a structured edit, leaving
  the elements it didn't ask to change exactly where they were. And
  nothing lands in the record without the clinician reading it first.
</Callout>

### NotePal: the note leaves the browser

The browser is not where a clinician works. Their patient management
system is the window that matters, and Clerkal spends most of its life
covering it up.

NotePal pops the template out into its own small window that floats on
top of whatever application is in front - the clinician works through
the note against the PMS on screen, then closes it and everything
returns to the main screen with nothing lost.

The part that made it hard is that it has to be one editor in two
windows, not a copy of one. Rendering the same live editor into a second
window means very little of what a browser normally hands you comes
along - styling, events, selection and the clipboard all belong to the
other window now. Get any of it slightly wrong and you have two editors
drifting apart, which for a clinical note is the worst failure mode
available: both copies look completely plausible.

### Paste is a protocol, not a feature

Clinicians arrive with a decade of notes in Word, Google Docs, Notepad
and rival EHRs, and they paste them in. Each of those sources hands the
clipboard a different, differently-broken flavour of HTML. So paste got
its own parsing layer: normalise the incoming markup per source, map it
onto our element tree, and drop everything that would poison the
document. Copy out runs the same road in reverse, because a note that
pastes into Word with invisible formatting artefacts is a note that
comes back as a support ticket.

### The performance problem, which was the real project

A production template is not a demo. It's hundreds - sometimes
thousands - of custom elements in one document. And the first honest
version of this editor re-rendered nearly all of them on every
keystroke.

The cause was a habit rather than a bug. The convenient way to reach the
editor from inside an element also subscribes that element to every
change anywhere in the document - and written that way in every element
type, one keystroke invalidates the entire tree. At fifty elements
nobody notices. At two thousand, typing lags, and clicking an option in
the medical history redraws the rest of the note with it.

<Callout label="What actually fixed it">
  Memoising every element, and then the unglamorous half: going through
  them one at a time so each element is handed exactly the data it needs
  instead of reaching into the document for it. An element then redraws
  when *its own* data changes, not when anything in the note does.
  Memoisation only pays once the inputs are stable, so most of the work
  was making them stable.
</Callout>

There was no clever trick at the end of it. It was a long stretch of
profiling, changing one element's prop contract, measuring, and moving
to the next - and it taught me more about React's actual rendering model
than any amount of reading had.

The other thing that consumed time and doesn't show up in a commit
graph: the animation and interaction polish. Dentists use this between
patients, sometimes gloved, often in a hurry, and almost none of them
think of themselves as software people. Every transition, hit target and
piece of feedback in the editor got argued over on those terms.

### Everything around the editor

The editor is the hard part but not the whole product. Alongside it:

- **Templates, folders and a shared library**, scoped by country and
  language, so a UK dental practice sees UK dental templates.
- **Teams and clinics** - sharing templates and documents across a
  practice, with clinic-level branding on patient-facing letters.
- **Role-based access control** over all of it: who can edit a shared
  template versus who can only use it, and what a clinic owner can do
  that a member can't.
- **Stripe subscriptions**, including group billing for clinics.
- **Redux Toolkit and RTK Query** for global state and the API layer,
  over a **Node.js / Express / MongoDB** backend that stores the
  document tree in the shape the editor already speaks.

<ExpandableDetail>

If I started this again, I'd version the element schema from the first
commit - every element type is a shape that now lives in real patients'
saved documents forever, and migrating that later is far more delicate
than getting it right early.

I'd also design the logic engine as a proper little language from day
one, rather than letting it grow out of the panel that configures it.
And I'd have written the performance rule down and enforced it
automatically - no element may reach into the whole document - instead
of relying on everyone remembering. That one rule, enforced early, would
have saved weeks of undoing it later.

### What I took from it

Most of what I learned here wasn't the editor library - it was how
React actually decides to redraw things, learned the hard way with a
profiler open, and the discipline of treating a document as structured
data with a contract rather than as markup you can nudge. The other half
is domain: when your user is a clinician between patients, the measure
of a feature isn't what it can do, it's how few gestures it takes and
how obviously it behaves.

### What it took to get there

- **A document model that holds up.** Ten-plus custom element types,
  each a stable shape that survives saving, sharing, duplicating and
  pasting between templates.
- **Performance at real scale.** Templates of thousands of elements that
  type without lag, after the re-render work above.
- **The seams that make the model useful.** Dictation, summarisation,
  cleanup and formatting that write back into the tree as structured
  edits rather than flattening it into dead text.
- **The product around it.** Templates, library, teams, clinics, RBAC,
  Stripe subscriptions and group billing.
