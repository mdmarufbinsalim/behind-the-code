<Expandable title="The problem" label="the constraints">

Qabiile is a gamified, invitation-only social network for the Turkish market.
Four tabs: **Agora**, the feed. **Reels**, short video. **Forest**, where
auction-style listings called hunts live. And **Qabile**, the clans - each one
carrying a reputation score and a global ranking that members push up
together.

Underneath all four sits a single number. Every post, reel, mission and hunt
win pays out **Qabi**, the in-app currency, and **EXP**, which moves an
account up a tier ladder that gates what it can reach. The balance is on
screen at all times, on every tab, next to a rank that people care about.

That is what makes it a different kind of build. A like that fails to
register is an annoyance. A bid moves currency out of one wallet and holds it
against another, and if two people bid at the same instant, someone's balance
is about to be wrong in a way that is very hard to explain afterwards.

Identity is the other half of it. Hunts are real trades between strangers, so
an account has to be provably a person - which for this market means reading
a Turkish national ID card, from a photo, taken by a user, in whatever
lighting they happened to be standing in.

<ExpandableDetail>

The constraints that shaped everything after this:

- **Every feature touches the wallet.** Onboarding steps, daily missions,
  posts, reels watched, surveys, hunt wins - they all pay out. There is no
  corner of this product where money is somebody else's problem, and the
  balance is visible on every screen, so a wrong number is never quiet.
- **Three clients, one API.** Web, mobile and admin all consume the same
  endpoints, and the mobile app ships on its own schedule. A silent response
  shape change is a broken release.
- **Two languages, from the first migration.** English and Turkish, including
  the strings the API itself returns.
- **One host, two environments.** Production and staging run on the same EC2
  box for cost reasons, which is fine right up until a deploy script points at
  the wrong checkout.
- **Small team, wide surface.** Six people building a feed, an auction house,
  a currency, a messaging system and a verification flow at the same time.

</ExpandableDetail>

</Expandable>

<Expandable title="The approach" label="the alternatives I ruled out">

One API owns the truth, and everything downstream is generated from it. The
NestJS app is a modular monolith - 31 modules with hard boundaries, each
owning its entities and its queues - rather than a constellation of services,
because six engineers cannot pay the operational tax of microservices and
still ship a feed.

The exception is where the work genuinely wasn't JavaScript. Reading an ID
card is CPU-bound image work with a native toolchain behind it, so it became
a separate Go worker with its own container, its own deploy, and no shared
runtime with the API at all.

<ContractFlow />

<ExpandableDetail>

What I ruled out, and why:

- **Microservices per domain.** The boundaries in this product are real, but
  they are transactional: bids touch wallets touch ledgers. Splitting those
  across services would have bought us distributed transactions in exchange
  for nothing we needed at this size.
- **Hand-written API clients.** Three codebases writing their own request
  types is three codebases that disagree by the end of the month. The API
  emits `openapi.json`, a package generates TypeScript from it, web and
  mobile consume the package. Break a response shape and their builds fail on
  the next generate.
- **An off-the-shelf KYC vendor.** Priced per check, and the market is narrow
  enough that the general-purpose vendors read Turkish cards poorly. The
  cards themselves are standardised and machine-readable - the MRZ at the
  bottom is designed to be parsed - so this was a solvable problem rather
  than a bought one.

</ExpandableDetail>

</Expandable>

### Getting in: invite-only, as a backend flow

Nobody signs up for Qabiile. An admin sends an invite, the code arrives by
email, and that code buys you exactly one thing: a short-lived registration
token, good only for finishing the registration it was issued for. Onboarding
arrives afterwards as a single request - avatar, interests, clan, together -
because a half-completed profile is not a state anyone wanted to support.

### Identity: reading a Turkish ID card in Go

The OCR service reads both halves of the card: the **MRZ**, the machine
readable strip along the bottom, which is fixed-format and reliable, and the
**VIZ**, the human-readable face of the card, which is a photograph of
printed text and is not. Both get extracted, and a failed read retries once
against an upscaled image before giving up.

The interesting part is the seam between the two runtimes.

<OcrPipeline />

**Why not BullMQ, when the API already runs BullMQ for everything else.**
BullMQ's job format is MessagePack and Lua-script driven, and it is not
documented as a stable wire protocol - it's an implementation detail of the
library, and the library is JavaScript. Reimplementing it in Go would have
meant tracking someone else's internals across versions forever. A JSON
payload on a plain Redis list is trivial to implement identically on both
sides, and the only thing the two codebases share is four key names.

**Why the key names look like that.** Production Redis is ElastiCache
Serverless, which runs in cluster mode, and `BRPOPLPUSH` touches two keys in
one call. Without the `{nidocr}` hash tag forcing both lists into the same
slot, every single call fails with `CROSSSLOT`. That hash tag is load-bearing
in two codebases at once, which is exactly the kind of thing that needs a
comment rather than a convention.

**Why `BRPOPLPUSH` rather than `BRPOP`.** The payload moves onto a processing
list before it is worked on and is removed only once it has been handled.
Crash a worker mid-job and the job is still sitting there, recoverable,
instead of having evaporated between the pop and the crash. The API's side of
this runs its own dedicated Redis connection, because a blocking command
monopolises whatever connection it runs on - sharing the app's client would
quietly wedge everything else.

**What comes back still has to be believed.** A successful read is not a
verification. The extracted fields get matched against what the user claimed,
with the small indignities that real documents involve: Turkish cards print
sex as `E/K` (Erkek/Kadın) on the visual side and `M/F` in the MRZ, so the
comparison normalises both alphabets before it decides anything. Anything
that doesn't match cleanly goes to a human in the admin queue.

### Money: a wallet that never gets edited

Every wallet balance in Qabiile is a cache. The truth is an append-only
ledger, and `balance`, `heldBalance` and `expBalance` are just the current
sum of entries against it. Nothing in the system ever writes a new number
into a wallet row and hopes.

<EarningLoop />

A bid is the one place where that ledger has to hold something back rather
than pay it out.

<EscrowLifecycle />

A bid is the hard case, because it is a hold rather than a payment. Placing
one runs in a transaction that takes a `pessimistic_write` lock on the hunt
row first - so simultaneous bids on the same hunt serialise on the hunt,
instead of racing each other through two different wallets in whatever order
they arrive and deadlocking when the lock ordering disagrees.

The hold writes a `held` ledger entry against the bidder's wallet. Get
outbid, and it writes a `released` entry that returns the money to spendable
balance. Win, and it settles: Qabi transfers, and the winner earns EXP worth
a tenth of what they spent, which is what moves them up the tiers the
platform gates access with.

Hunts close on a scheduler that runs every minute, picks up any published
hunt past its window, and captures the winning bid. It is deliberately
self-healing: it looks for expired hunts rather than trusting a timer it set
earlier, so a restart in the middle of the night doesn't leave a hunt open
forever.

### Everything that happens after the response

Six BullMQ workers do the things nobody should wait for: transactional mail,
reel transcoding, search indexing, payments, hunt expiry, survey expiry. The
reels pipeline is the heaviest of them.

<ReelPipeline />

Realtime runs on a Socket.io gateway with a session registry mapping users to
sockets, plus an internal endpoint that lets other modules push events without
importing the gateway - the alternative being every module reaching into the
socket layer and the whole thing becoming impossible to reason about.

### The web app: four tabs and a wallet in the header

The web client is Next.js 16 on the App Router, and its route groups are the
product's own shape: `(public)` for the marketing site and the legal pages,
`(auth)` for invitation, OTP, sign-in and account deletion, `(request)` for
request-access, and `(app)` for everything behind the wall - the four user
tabs, onboarding, and a separate admin area.

None of the client types are hand-written. The web app consumes the same
generated contracts package the mobile app does, through `openapi-fetch`, so
a response shape that changes in the API fails the web build rather than
failing a user.

The frontend problems worth naming:

- **The balance is in the header, on every page.** Finishing a mission in one
  tab has to move the number in the chrome of another. That is Redux Toolkit
  holding wallet state, refreshed off the same socket that delivers
  notifications - not a page reload, and not a poll.
- **Reels play the transcoder's output.** `hls.js` in the browser, pointed at
  the multi-rendition HLS the reels worker wrote to S3, with the watch and
  reward events the backend counts fired from the player itself.
- **Buying Qabi is a real payment.** Stripe Elements on the front, the
  payments queue on the back, and a wallet that must not credit twice if a
  webhook arrives twice.
- **Two languages, one component tree.** `next-intl` carries EN and TR
  through the UI, matched by the API's own message catalogues, so an error
  toast and the error behind it are in the same language.
- **The awkward, unglamorous surfaces.** Avatar cropping in onboarding, OTP
  inputs that handle paste, an emoji picker and attachments in chat, a
  masonry grid for media, a lightbox for post images. None of it is hard.
  All of it is the difference between a demo and something people use.

### The parts that are only visible when they're missing

- **Search** runs on Typesense, indexed by a queue worker fed from entity
  subscribers, so a new post is searchable without the write path waiting for
  an index round-trip.
- **Localisation** covers the API's own responses, not just the clients:
  English and Turkish message catalogues resolved per request.
- **Rate limiting** is Redis-backed rather than in-memory, because two
  containers with their own counters is not a rate limit.
- **Account deletion and retention** exist as first-class flows - a deletion
  request, a grace period, and a scheduler that actually removes the data.

### Shipping it on one box

Production and staging run on the same EC2 instance as two Compose projects
with two checkouts, behind a single Caddy that terminates TLS for four
hostnames and renews its own certificates. Two GitHub Actions workflows, one
per branch, SSH in, check out, build the three images in sequence to keep
peak memory under control, and bring the stack up.

Two details that took an incident each to learn: the staging workflow refuses
to run unless its target directory ends in `-staging`, so a copied production
secret can't overwrite the production checkout; and the deploy prunes build
cache older than 72 hours rather than all of it, because wiping the cache on
every deploy turns a two-minute deploy into a full reinstall and recompile.

### What leading it actually meant

The technical decisions that were expensive to reverse were mine to make: the
module boundaries, the append-only ledger, a generated contract instead of
hand-written clients, and a separate runtime for the one job that wasn't
JavaScript. But most of the work of leading wasn't architecture - it was
making the same decisions legible to five other people so they could build
against them without asking me first.

That is why this repo has a long knowledge base rather than a thin README, why
the deploy notes explain why the build cache is preserved rather than just
telling you not to wipe it, and why the seams between modules are where the
comments are. A team of six moving fast is worth much more than any individual
decision I made about a queue.

I also wrote the parts where being wrong costs the most - the wallet and
bidding code, the verification pipeline, the web client's session and wallet
plumbing, the deployment - and reviewed the rest.

### What I'd do differently

**Phase the product harder.** Feed, reels, clans, messaging, an auction house
and a currency all reached Phase 1 together. Every one of them is defensible
on its own, and the sum of them is why some things are shallower than I would
like. I would fight for a narrower Phase 1 next time, and I would lose that
fight more slowly.

**Write the shared decisions down first, not after.** The best documentation
in this project was written when something had already gone wrong twice. The
knowledge base should have started on day one, alongside the first module.

**Stop implementing the same idea twice in two languages.** The reliable-queue
loop exists in Node and in Go, written from the same paragraph of reasoning on
two different days. A one-page spec would have made the second one a
transcription rather than a translation.

### What I took from it

That the hard parts of a social product are rarely the social parts. They are
the ones any bank would recognise: what is the source of truth for a balance,
what happens when two writes land together, what do you do when a job dies
halfway through.

And that leading a team is mostly about reducing the number of things everyone
else has to hold in their head. The contract is generated so nobody has to
remember a response shape. The ledger is append-only so nobody has to reason
about who last edited a balance. Every one of those choices costs something up
front and pays back every week afterwards, in questions that never get asked.
