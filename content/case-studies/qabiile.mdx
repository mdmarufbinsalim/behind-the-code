<Expandable title="The problem" label="the constraints">

Qabiile is an invitation-only social platform for the Turkish market, built
on one idea: everything you do there earns you something. Posting, watching a
video, finishing a daily challenge, winning an auction - all of it pays out in
the platform's own currency, and in experience that moves your account up a
ladder of ranks. Your balance and your rank follow you across every screen.

That turns a social app into something closer to a small bank. A like that
fails to register is an annoyance; currency that lands in the wrong place is
an argument with a real person about money they earned. And because members
trade real goods with strangers, an account has to be provably a real person -
which in this market means checking a government ID.

I came in as team and dev lead: six engineers across the API, the web app and
the mobile app, with me responsible for the architecture, for the parts where
a mistake is expensive, and for making the decisions everyone else builds
against clear enough that nobody has to ask.

<ExpandableDetail>

The constraints that shaped everything after this:

- **Every feature touches the wallet.** Onboarding steps, daily missions,
  posts, reels watched, surveys, hunt wins - they all pay out. There is no
  corner of this product where money is somebody else's problem, and the
  balance is visible on every screen, so a wrong number is never quiet.
- **Three clients, one API.** Web, mobile and admin all consume the same
  endpoints, and the mobile app ships on its own schedule. A silent response
  shape change is a broken release.
- **Two languages, from the first migration.** English and Turkish, including
  the strings the API itself returns.
- **One host, two environments.** Production and staging run on the same EC2
  box for cost reasons, which is fine right up until a deploy script points at
  the wrong checkout.
- **Small team, wide surface.** Six people building a feed, an auction house,
  a currency, a messaging system and a verification flow at the same time.

</ExpandableDetail>

</Expandable>

<Expandable title="The approach" label="the alternatives I ruled out">

One API holds the truth, and every client is generated from it rather than
written by hand. The server is a single well-partitioned application rather
than a fleet of small ones, because a team this size pays for every extra
moving part in operations instead of in features.

The one exception is identity verification. Reading an ID card out of a
photograph is a different kind of work with a different toolchain behind it,
so it runs as its own small service, in Go, with no shared runtime with the
rest.

<ContractFlow />

<ExpandableDetail>

What I ruled out, and why:

- **Microservices per domain.** The boundaries in this product are real, but
  they are transactional: bids touch wallets touch ledgers. Splitting those
  across services would have bought us distributed transactions in exchange
  for nothing we needed at this size.
- **Hand-written API clients.** Three codebases writing their own request
  types is three codebases that disagree by the end of the month. The API
  emits `openapi.json`, a package generates TypeScript from it, web and
  mobile consume the package. Break a response shape and their builds fail on
  the next generate.
- **An off-the-shelf KYC vendor.** Priced per check, and the market is narrow
  enough that the general-purpose vendors read Turkish cards poorly. The
  cards themselves are standardised and machine-readable - the MRZ at the
  bottom is designed to be parsed - so this was a solvable problem rather
  than a bought one.

</ExpandableDetail>

</Expandable>

### Getting in: invite-only, as a backend flow

Nobody signs up for Qabiile. An admin sends an invite, the code arrives by
email, and that code buys you exactly one thing: a short-lived registration
token, good only for finishing the registration it was issued for. Onboarding
arrives afterwards as a single request - avatar, interests, clan, together -
because a half-completed profile is not a state anyone wanted to support.

### Identity: reading a Turkish ID card in Go

A Turkish ID card carries the same information twice: once as printed text a
human reads, and once as a machine-readable strip designed to be parsed. The
service reads both, because the strip is reliable and the printed face is a
photograph taken in whatever lighting the user was standing in. A failed read
gets one retry against a cleaned-up image before it gives up.

<OcrPipeline />

Three decisions worth the space:

**It runs as its own service, in another language.** Image work is CPU-bound
and wants a native toolchain, and running it inside the API would mean one bad
photo could slow down the feed. As a separate worker it can be starved,
restarted or scaled without anything else noticing.

**The two sides talk through a deliberately dumb queue.** The API already runs
a job library, but that library's job format is a JavaScript implementation
detail, not a documented protocol - reimplementing it in Go would have meant
tracking someone else's internals forever. Instead both sides agree on a
plain list of JSON messages, which is a page of code in either language. The
queue is arranged so that a worker dying mid-job leaves the job recoverable
rather than lost, which matters when the job is someone's identity check.

**A successful read is not a verification.** What comes back gets matched
against what the user claimed about themselves, and anything that doesn't
line up cleanly goes to a human in the admin queue rather than being waved
through or rejected outright. The automation is there to make the reviewer's
job small, not to replace them.

### Money: a wallet that never gets edited

No balance in Qabiile is ever edited. Every wallet is a running total of an
append-only list of entries - earned here, spent there, held against a bid -
so the number on screen can always be explained by pointing at the entries
that produced it. This is the single decision the rest of the money code
depends on: there is no code path anywhere that writes a new balance and
hopes.

<EarningLoop />

A bid is the hard case, because it has to hold money without spending it. The
amount is held against the bidder's wallet while the auction runs, released
the moment they're outbid, and settled only if they win. Two people bidding at
the same instant are serialised on the listing itself, so the last write can't
quietly overwrite the one before it - the failure mode I care about here isn't
a slow bid, it's two people who both believe they won.

<EscrowLifecycle />

Auctions close on a sweep that looks for listings past their deadline, rather
than on a timer set when the listing was created. Timers don't survive
restarts; a sweep does, and it heals anything an outage left half-finished.

### Everything that happens after the response

Anything slow happens after the response: sending mail, processing uploaded
video, indexing for search, settling payments, closing auctions. The video
pipeline is the heaviest - an upload is accepted immediately and only becomes
playable once a worker has transcoded it into the formats a phone can stream.

<ReelPipeline />

Realtime - messages, notifications, live bid updates - runs over a socket
layer that the rest of the application talks to through one internal seam
rather than by reaching into it directly. That seam is the only reason the
messaging feature didn't end up entangled with everything else.

### The web app: four tabs and a wallet in the header

The web app is Next.js on the App Router, and its structure mirrors the
product: a public marketing side, an invitation and sign-in flow, and
everything behind the wall - the four tabs, onboarding, and a separate admin
area for the people who run the platform.

None of its API types are written by hand - it consumes the same generated
package the mobile app does, so a change to a response shape breaks a build
instead of a user.

The three frontend problems that actually took thought:

- **The balance is in the header of every page.** Finishing a challenge in one
  part of the app has to move a number in the chrome of another, live, without
  a reload or a poll. Wallet state is held centrally and refreshed off the same
  socket that carries notifications.
- **Paying real money for in-app currency.** Card payments on the front,
  settlement on a queue at the back, and a wallet that must not credit twice
  if the payment provider tells us the same thing twice.
- **Two languages through one component tree.** English and Turkish across the
  UI, matched by the API's own translated responses, so an error message and
  the error behind it are never in different languages.

### The parts that are only visible when they're missing

- **Search** runs on Typesense, indexed by a queue worker fed from entity
  subscribers, so a new post is searchable without the write path waiting for
  an index round-trip.
- **Localisation** covers the API's own responses, not just the clients:
  English and Turkish message catalogues resolved per request.
- **Rate limiting** is Redis-backed rather than in-memory, because two
  containers with their own counters is not a rate limit.
- **Account deletion and retention** exist as first-class flows - a deletion
  request, a grace period, and a scheduler that actually removes the data.

### Shipping it on one box

Production and staging run on the same server as two separate stacks, behind
one reverse proxy that handles TLS for both and renews its own certificates.
Each branch has its own deploy pipeline, and the staging pipeline physically
cannot write to the production checkout - a guard that exists because the cost
of getting that wrong once is much higher than the cost of the guard.

The other lesson was cheaper to learn and easy to forget: a deploy that throws
away its build cache every time turns a two-minute release into a full rebuild,
so the pipeline keeps recent cache deliberately.

### What leading it actually meant

The technical decisions that were expensive to reverse were mine to make: the
module boundaries, the append-only ledger, a generated contract instead of
hand-written clients, and a separate runtime for the one job that wasn't
JavaScript. But most of the work of leading wasn't architecture - it was
making the same decisions legible to five other people so they could build
against them without asking me first.

That is why this repo has a long knowledge base rather than a thin README, why
the deploy notes explain why the build cache is preserved rather than just
telling you not to wipe it, and why the seams between modules are where the
comments are. A team of six moving fast is worth much more than any individual
decision I made about a queue.

I also wrote the parts where being wrong costs the most - the wallet and
bidding code, the verification pipeline, the web client's session and wallet
plumbing, the deployment - and reviewed the rest.

### What I'd do differently

**Phase the product harder.** Feed, reels, clans, messaging, an auction house
and a currency all reached Phase 1 together. Every one of them is defensible
on its own, and the sum of them is why some things are shallower than I would
like. I would fight for a narrower Phase 1 next time, and I would lose that
fight more slowly.

**Write the shared decisions down first, not after.** The best documentation
in this project was written when something had already gone wrong twice. The
knowledge base should have started on day one, alongside the first module.

**Stop implementing the same idea twice in two languages.** The reliable-queue
loop exists in Node and in Go, written from the same paragraph of reasoning on
two different days. A one-page spec would have made the second one a
transcription rather than a translation.

### What I took from it

That the hard parts of a social product are rarely the social parts. They are
the ones any bank would recognise: what is the source of truth for a balance,
what happens when two writes land together, what do you do when a job dies
halfway through.

And that leading a team is mostly about reducing the number of things everyone
else has to hold in their head. The contract is generated so nobody has to
remember a response shape. The ledger is append-only so nobody has to reason
about who last edited a balance. Every one of those choices costs something up
front and pays back every week afterwards, in questions that never get asked.
